# Learning Content Standard

> **Constitution Documentation**
>
> This document defines the official learner-facing content standard for the
> `fribot-learning` repository.
>
> It translates the Learning Constitution into practical standards for
> designing Starter Projects, project documentation, executable learning
> materials, and learner experiences.
>
> The constitutional source of truth remains the
> `fribot-labs/innermirror-constitution` repository.
>
> This document defines **how educational content should be written**.
>
> It does not redefine constitutional meaning.

---

# Purpose

The purpose of this document is to ensure that every learner-facing project
provides a consistent educational experience.

Every Starter Project should:

- create a meaningful experience,
- encourage observation,
- enable comparison,
- support understanding,
- naturally lead toward Reflection.

This document standardizes how those experiences are designed.

---

# Constitutional Basis

The Learning Constitution defines the following permanent principles.

- Learning Principle Zero
- Comparison-Based Learning
- Experience Before Explanation
- Reflection Emergence

These principles are implemented through learner-facing content.

Educational content should therefore be designed around learning
experiences rather than information delivery.

---

# Learning Philosophy

Traditional documentation often follows this structure.

```text
Explain

↓

Example

↓

Exercise
```

Fribot Learning follows a different structure.

```text
Expectation

↓

Execution

↓

Observation

↓

Comparison

↓

Explanation

↓

Understanding

↓

Reflection
```

Understanding grows from meaningful experience.

Documentation should preserve this progression whenever appropriate.

---

# Standard Learning Flow

Every Starter Project should support the following constitutional learning
flow.

```text
Predict

↓

Run

↓

Observe

↓

Compare

↓

Understand

↓

Reflect
```

These stages do not necessarily require identical file names.

However,

the learner should naturally experience each stage.

---

# Starter Project Standard

A standard Starter Project should normally include:

```text
README.md

EXPECTED_OUTPUT.md

RUN.md

TROUBLESHOOTING.md

WHY_IT_WORKS.md

BEFORE_YOU_CONTINUE.md
```

Additional documents may be added when appropriate.

Each document should have one clearly defined educational purpose.

---

# README.md

## Purpose

Provide orientation.

The README should answer:

- What is this project?
- What will the learner build?
- Why is this project interesting?
- What experience should the learner expect?

The README should avoid explaining every concept in advance.

Its purpose is to prepare the learner,

not replace discovery.

---

# EXPECTED_OUTPUT.md

## Purpose

Create an expectation.

The learner should be able to predict:

- expected behavior,
- expected output,
- expected interaction,
- expected observations.

The learner should compare this expectation with reality after execution.

EXPECTED_OUTPUT should not reveal every explanation.

It establishes the learner's mental model before execution.

---

# RUN.md

## Purpose

Create direct experience.

RUN should help learners:

- execute the project,
- verify the environment,
- observe the first successful result.

Execution should occur before detailed conceptual explanation whenever
possible.

---

# TROUBLESHOOTING.md

## Purpose

Support observation.

Troubleshooting is not merely error correction.

It helps learners investigate:

- unexpected behavior,
- incorrect assumptions,
- environmental differences,
- implementation differences.

Troubleshooting strengthens understanding by encouraging careful
observation.

---

# WHY_IT_WORKS.md

## Purpose

Explain experienced behavior.

WHY_IT_WORKS should connect:

- observed behavior,
- underlying concepts,
- architectural relationships,
- engineering reasoning.

Explanation should answer questions already created through experience.

It should not remove the learner's opportunity for discovery beforehand.

---

# BEFORE_YOU_CONTINUE.md

## Purpose

Recognize changed understanding.

The learner should pause and ask:

- What surprised me?
- What now seems obvious?
- What changed?
- Which relationship became visible?
- What question do I now have?

This document prepares the learner for Reflection.

---

# Reflection

Reflection is not another document requirement.

Reflection is the natural continuation of meaningful understanding.

The repository should create opportunities for Reflection.

InnerMirror preserves Reflection.

Their responsibilities remain separate.

```text
Fribot Learning

↓

Learning Experience

↓

Changed Understanding

↓

Reflection

↓

InnerMirror
```

---

# Comparison Standard

Every substantial project should intentionally include at least one
meaningful comparison.

Possible comparisons include:

- expected vs actual behavior,
- before vs after modification,
- procedural vs class-based implementation,
- one MCU vs two MCUs,
- centralized vs distributed responsibility,
- learner implementation vs AI implementation.

Comparison should be explicitly designed rather than left to chance.

---

# Explanation Standard

Explanation should:

- follow meaningful experience,
- answer learner questions,
- explain observed behavior,
- reveal structural relationships,
- strengthen understanding.

Explanation should not simply transfer information.

It should connect experience with meaning.

---

# AI Era Learning

Artificial intelligence changes how educational content should be designed.

AI can generate:

- code,
- explanations,
- documentation,
- examples.

Therefore,

educational content should increasingly emphasize:

- observation,
- comparison,
- experimentation,
- architectural reasoning,
- changed understanding.

AI accelerates implementation.

Learning transforms understanding.

These responsibilities remain distinct.

---

# Writing Style

Educational documents should be:

- clear,
- concise,
- observable,
- experience-oriented,
- comparison-oriented,
- implementation-aware.

Prefer:

- active language,
- learner questions,
- observable outcomes,
- engineering relationships.

Avoid:

- excessive theoretical exposition,
- unnecessary abstraction before experience,
- revealing every conclusion before execution,
- duplicating the same explanation across multiple documents.

---

# Project Completion Standard

A learning project should allow the learner to:

- execute a working baseline,
- observe meaningful behavior,
- modify one important aspect,
- compare meaningful differences,
- understand at least one engineering relationship,
- recognize a change in understanding,
- naturally transition toward Reflection.

Working software alone does not complete a learning experience.

Meaningful understanding completes it.

---

# Content Review Checklist

Before publishing learner-facing content, confirm:

- [ ] Does this create a meaningful learner experience?
- [ ] Can the learner form an expectation?
- [ ] Is the result observable?
- [ ] Is at least one meaningful comparison designed?
- [ ] Does explanation follow experience?
- [ ] Does the learner have an opportunity to recognize changed understanding?
- [ ] Is Reflection naturally supported?
- [ ] Are repository boundaries preserved?

# Long-Term Vision

Educational technologies will continue changing.

Programming languages,

robotics platforms,

AI systems,

and development environments

will all evolve.

The constitutional learning principles should remain stable.

Future educational content should continue implementing those principles
regardless of technological change.

---

# Foundation Principle

Learning content should not begin by maximizing explanation.

Learning content should create meaningful experiences through which learners
can observe, compare, understand, and naturally recognize changes in their
own thinking.

Projects create experience.

Experience creates comparison.

Comparison transforms understanding.

Reflection preserves growth.
