# Service Responsibility Matrix

> **Architecture Documentation**
>
> This document defines the service-level responsibility matrix of the Fribot
> and InnerMirror ecosystem.
>
> Unlike repository responsibility documents, which assign ownership to
> repositories, this document assigns responsibilities to architectural
> service layers.
>
> It translates the constitutional architecture into service-level
> boundaries.
>
> The constitutional source of truth remains the
> `fribot-labs/innermirror-constitution` repository.
>
> Service layers implement constitutional responsibilities.
>
> They do not redefine constitutional meaning.

---

# Constitutional Basis

The ecosystem is governed by three constitutional layers.

```text
Human Growth Constitution

↓

Learning Constitution

↓

Runtime Constitution
```

These constitutional layers are implemented through distinct service
responsibilities.

```text
Learning Experience

↓

Reflection Interface

↓

Private Runtime Intelligence

↓

Long-Term Continuity
```

The Learning layer creates transformation.

The Landing layer enables human interaction.

The Runtime layer preserves continuity.

The Engine explores future intelligence.

---

# Purpose

The Fribot and InnerMirror ecosystem consists of multiple independent service
layers.

Each service layer owns one primary architectural responsibility.

The purpose of this document is to preserve clear separation among:

- learner-facing experience,
- Reflection interaction,
- private Runtime processing,
- experimental intelligence.

This separation allows the ecosystem to evolve without creating overlapping
responsibilities.

Every feature should be assigned to one primary service responsibility before
implementation begins.

# Learning Service Layer

## Primary Repository

```text
fribot-learning
```

## Primary Responsibility

The Learning layer creates meaningful learner-facing experiences.

It implements the Learning Constitution through projects, executable
materials, observation, comparison, and explanation after experience.

---

## Owns

- learner-facing project experiences,
- Starter Projects,
- project progression,
- controlled modifications,
- executable examples,
- expected-output guidance,
- troubleshooting guidance,
- meaningful comparison,
- educational explanation,
- Reflection transition guidance,
- public learning documentation.

---

## Constitutional Flow

The Learning layer should preserve the following progression whenever
applicable.

```text
Predict

↓

Run

↓

Observe

↓

Compare

↓

Understand

↓

Reflect
```

The Learning layer may create the conditions in which Reflection becomes
meaningful.

It does not privately interpret the learner.

---

## Does Not Own

- private Reflection analysis,
- continuity scoring,
- long-term learner memory,
- identity interpretation,
- coaching-strategy selection,
- Runtime orchestration,
- user-interface presentation.

---

## Service Question

A feature belongs to the Learning layer when its primary purpose is:

> To help the learner experience, run, observe, compare, understand, or move
> naturally toward Reflection.

# Reflection as the Service Bridge

Reflection is the primary bridge between Learning and Runtime.

```text
Learning Experience

↓

Changed Understanding

↓

Reflection

↓

Runtime Continuity
```

The Learning layer creates the experience.

Landing receives the learner's Reflection.

Runtime privately preserves and interprets continuity.

This division should remain explicit.

Learning does not generate private cognitive conclusions.

Runtime does not create learner-facing project experiences.

# Service Communication Rules

Service layers communicate through stable and explicit contracts.

```text
Landing

↓

Versioned Runtime Contract

↓

Runtime

↓

Structured Runtime Response

↓

Landing
```

Where project context is passed:

```text
Learning Service

↓

Public Project Context

↓

Landing or Runtime Contract
```

No service should access another service's private internal implementation
directly.

---

# Contract Principles

A service contract should define:

- contract version,
- request fields,
- response fields,
- optional fields,
- validation rules,
- error behavior,
- privacy boundaries,
- field ownership,
- compatibility expectations.

Contracts should expose only the information required for approved
collaboration.

They should not expose:

- internal reasoning traces,
- private prompts,
- raw memory structures,
- unapproved experimental scores,
- unnecessary personal context.

# MVP Integration Policy

The MVP intentionally uses user-triggered synchronization.

Current workflow:

```text
Reflection

+

Reflect + GitHub Analyze

↓

Authorized GitHub Snapshot

↓

Runtime Analysis

↓

Structured Result
```

The MVP excludes:

- background repository monitoring,
- automatic Reflection generation,
- GitHub Webhooks,
- background schedulers,
- continuous polling,
- silent cognitive analysis,
- automatic cross-service synchronization.

Manual operation should first demonstrate educational and product value.

---

# Service Independence

Every service layer should remain independently maintainable.

A service should be:

- independently testable,
- independently replaceable where practical,
- internally evolvable,
- connected through explicit contracts,
- resilient to partial system failure.

Independence does not mean isolation.

It means that collaboration does not erase ownership.

---

# Failure Isolation

## Runtime Unavailable

Landing should:

- preserve user input where appropriate,
- present a clear recoverable error,
- avoid presenting simulated private analysis as real analysis.

Learning materials should remain available.

---

## GitHub Context Unavailable

Reflection should remain possible when the approved contract does not require
GitHub context.

GitHub data is supplementary unless explicitly required.

---

## Learning Service Unavailable

InnerMirror should still support general Reflection that does not originate
from a Fribot Learning project.

---

## Engine Unavailable

Production Runtime should remain unaffected.

Research must not become a hidden production dependency.

---

# Future Expansion

Future services should follow the same architectural principle.

Possible future responsibilities include:

- domain-specific learning services,
- team learning,
- enterprise administration,
- approved analytics,
- learning-resource marketplaces,
- additional private continuity services.

A new service layer should be introduced only when:

- a stable independent responsibility exists,
- existing layers cannot own it clearly,
- a contract can be defined,
- privacy and security boundaries are explicit,
- lifecycle and primary ownership are documented.

---

# Maintenance Policy

This Service Responsibility Matrix should be updated when:

- a new service layer is introduced,
- a primary responsibility changes,
- a production responsibility moves between layers,
- a research responsibility is promoted,
- a contract materially changes the service boundary.

Routine implementation details should not require modification to this
document.

---

# Service Review Checklist

Before merging a service-boundary-sensitive feature, confirm:

- [ ] The primary service responsibility is identified.
- [ ] The owning repository is correct.
- [ ] Learning experience and private interpretation remain separated.
- [ ] Reflection input and Runtime analysis remain separated.
- [ ] Presentation and intelligence are not duplicated.
- [ ] Runtime continuity remains private.
- [ ] Engine research has not entered production without review.
- [ ] Contracts are explicit.
- [ ] Shared data is minimized.
- [ ] User authorization is preserved.
- [ ] Failure behavior is documented.
- [ ] Related architecture documents are updated.
