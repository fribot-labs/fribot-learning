# Class Concept Robot

> Status: MVP Project (Planned)  
> Project ID: `class-concept-robot`  
> Difficulty: Beginner → Early Intermediate  
> Estimated Duration: 3–7 Days

---

# Project Purpose

This project introduces one of the most important concepts in software engineering:

> **Why do classes exist?**

Most beginners first encounter classes as a new C++ syntax.

This project intentionally follows a different path.

The learner first experiences:

- working procedural code,
- small modifications,
- growing complexity,

before gradually discovering why software begins to group related state and behavior into one object.

The objective is **not** to memorize C++ syntax.

The objective is to understand **why software structure changes as projects grow**.

---

# Why This Project?

Many coding courses introduce classes immediately.

Typical learning order:

```text
class

↓

object

↓

constructor

↓

member variable

↓

method
```

The learner memorizes syntax before understanding why it exists.

This project reverses that order.

The learner first experiences:

```text
Working Code

↓

Controlled Modification

↓

Growing Complexity

↓

Need for Better Structure

↓

Class
```

Instead of asking:

> "How do I write a class?"

the learner begins asking:

> **"Why is a class useful here?"**

That question becomes the foundation of later software engineering.

---

# Learning Goal

By completing this project, the learner should understand that a class is not merely a C++ language feature.

The learner should begin recognizing a class as a way to organize:

- related information,
- related behavior,
- one clear responsibility.

The learner is **not** expected to master object-oriented programming.

The learner is expected to discover why classes naturally appear as software grows.

# What You Will Build

The learner will work with a small coding robot example.

The robot should be capable of performing simple observable actions.

Examples include:

- moving forward,
- stopping,
- changing speed,
- turning,
- reading sensor values.

The exact implementation is less important than observing how the code changes as functionality grows.

---

# What You Will Learn

By the end of the project, the learner should begin understanding:

- object,
- state,
- behavior,
- member variable,
- method,
- public interface,
- private boundary,
- responsibility.

The learner is **not** expected to master every topic.

The project focuses on recognizing the relationships between them.

# Project Stages

## Stage 1 — Start

Prepare the development environment.

Understand:

- the project goal,
- required hardware,
- required software,
- expected result.

---

## Stage 2 — Run

Run the prepared robot example.

Observe the original behavior.

Confirm that the project works before making changes.

---

## Stage 3 — Modify

Change one controlled part of the project.

Examples:

- movement speed,
- movement duration,
- stopping behavior,
- one class member,
- one method.

Observe how the modification changes the visible behavior.

---

## Stage 4 — Understand

Compare the original structure with the modified version.

Begin asking:

- What information should be remembered?
- What behavior belongs together?
- Why might these responsibilities be grouped?

This stage introduces the meaning behind classes.

---

## Stage 5 — Reflect

Write a normal InnerMirror Reflection.

The project does not evaluate your answer.

Instead, it asks one question.

Example:

> **How has your understanding of classes changed since beginning this project?**

# Completion Criteria

The project is complete when the learner can:

- execute the original project,
- make one controlled modification,
- explain one structural difference,
- identify one responsibility,
- describe why grouping related state and behavior may be useful,

The learner is **not** expected to design a complete object-oriented architecture.

# What This Project Does Not Teach

This project is intentionally limited.

It does **not** attempt to teach:

- inheritance,
- polymorphism,
- advanced design patterns,
- SOLID principles,
- UML,
- enterprise architecture,
- software frameworks.

Those topics belong to later projects.

The first objective is much simpler.

> **Understand why classes begin to appear naturally as software grows.**

---

# Foundation Principle

A learner should first experience a working system.

Only then should the learner begin asking:

> **Why was the software organized this way?**

This project is designed to help that question emerge naturally through practical experience rather than through memorization of programming syntax.
